# 몬스핀 저장 데이터 변경

공통 규칙은 [AGENTS.md](../../../AGENTS.md), 데이터 의미와 호환성 기준은 [README의 공통 코드와 데이터 설계 기준](../../../README.md#공통-코드와-데이터-설계-기준)을 따른다. 이 스킬은 저장 변경의 영향 분석·구현·검증 절차를 다룬다.

## 영향과 보존 대상 확인

- 관련 모델과 도메인 목록에서 필드의 의미를 확인하고, `src/data/`의 읽기·쓰기 함수부터 사용하는 훅과 화면까지 참조를 추적한다.
- `src/data/database.ts`에서 현재 스키마, `user_version`, 해당 마이그레이션과 제약 조건을 확인한다. 월별 기록·금액 이력을 건드릴 때만 README의 해당 동작과 `ledger.ts`, `expense-amount-history.ts`를 추가로 읽는다.
- 변경할 값, 기존 값의 처리 방법, 보존할 ID·관계·정렬·월 기록을 정리한다. 기존 값의 의미를 확정할 수 없으면 임의 매핑하지 않고 보존 방법을 설계하며, 제품 판단이 필요한 부분만 사용자에게 확인한다.

## 저장 변경 구현

- 모델·공통 목록·저장 검증·DB 제약·읽기 변환을 변경 영향에 맞게 함께 수정한다. 표시명만 변경한다면 저장 코드나 스키마를 불필요하게 바꾸지 않는다.
- 스키마 변경이 필요하면 신규 설치용 정의와 기존 설치용 이전 경로를 모두 반영한다. 이전에 배포한 마이그레이션만 덮어써 이미 업데이트한 기기의 변경을 누락하지 않는다.
- 연결된 여러 변경은 기존 트랜잭션 경계에 맞춰 원자적으로 처리하고, 실패 시 부분 저장이나 잘못된 스키마 버전이 남지 않도록 한다.
- 변경한 저장 결과가 훅과 화면에 반영되는 흐름을 연결한다. 현재 도입하지 않은 서버나 동기화 구조까지 범위를 확대하지 않는다.

## 실제 저장 결과 검증

- `tests/domain.test.cjs`의 기존 SQLite 테스트 방식을 활용해 변경된 저장 동작의 회귀 검증을 추가·수정하고 `npm test`를 실행한다.
- 스키마나 저장 코드 이전이 있다면 영향받는 기존 버전의 데이터와 신규 DB를 모두 확인한다. 이전 후 재접속과 재실행에서 데이터·참조가 유지되고 이전이 중복 적용되지 않는지 검증한다.
- 트랜잭션·마이그레이션이 바뀌면 중간 실패 후 롤백과 재시도를 검증한다. 유효하지 않은 코드·관계를 거부해도 기존 데이터는 유지되어야 한다.
- 변경과 관련된 경우에만 미입력과 0원, 중복 이름의 서로 다른 ID, 월 경계, 자동 내역과 직접 입력 금액, 과거 기록 보존을 확인한다.
- 데이터 의미·저장 구조·이전 동작이 달라지면 README의 해당 설명을 갱신한다. AGENTS.md의 공통 완료 기준을 적용하고 기존 데이터 처리 방식과 검증 결과를 보고한다.
